# Graphics Review

Scope: `src/Robotron2084/Graphics/*.cs`, excluding `Graphics/Models`.

## Findings

### Medium — pass-through restoration depends on the effect's current technique

`BlitterDraw.UsePassThrough()` restores `effect.CurrentTechnique.Passes[0]` (`BlitterDraw.cs:255-260`) rather than explicitly selecting the pass-through/Main technique. Calls that apply GlyphCycle or SolidRemap then call this method immediately after queuing a sprite draw. Although `SpriteBatch` is using `SpriteSortMode.Immediate`, a custom pass remains device state for subsequent work, and the safe behavior is to bind MainTech explicitly. If `CurrentTechnique` is changed or diverges from MainTech, this restoration can leave the batch in a remap or glyph pass. The name-based lookup used for GlyphCycle and SolidRemap should be mirrored for pass-through state restoration.

### Medium — pixel collision scales one axis with only one sprite dimension

`SpriteMask.Overlaps()` derives `cell` solely from `firstDrawnBounds.Width / firstSpriteMask.Width` and reuses it for vertical mapping and for neither sprite independently (`SpriteMask.cs:80-91`). The public API has no requirement that both masks use the same uniform scale or that drawn bounds have a square cell. A rectangle mask or non-square drawn bounds can therefore map `y`, and/or the second sprite, to the wrong mask row. This is especially important because a texture can be wider or taller than a collision box and the collision contract accepts arbitrary `Rectangle` values. The implementation should calculate separate X/Y sample scales for each sprite and verify dimensions are positive.

### Low — mask construction and overlap do not fully validate ranges

`SpriteMask.CreateFromPixels()` writes directly to `isOpaque[y * width + x]` and does not reject negative or out-of-range coordinates (`SpriteMask.cs:39-47`). Invalid input throws an `IndexOutOfRangeException`, while a valid mask API can instead define it out of bounds. `Overlaps()` can also divide by zero or produce zero-scaled mappings for zero-width masks or zero-sized drawn bounds. These conditions are not currently reached through normal `TextureSet` frames, but they are avoidable edge failures at the public utility boundary.

### Low — Williams blit is missing explicit lower and left clipping guards

`WilliamsLogoBorder.Blit()` checks `screenX < Width` and `screenY < Height`, but not `screenX >= 0` or `screenY >= 0` (`WilliamsLogoBorder.cs:158-164`). The built-in path values are currently positive and in range, so the normal attract sequence remains safe, but the method performs array indexing on out-of-range coordinates if `_logoSpriteMask` or path state becomes invalid. An explicit four-sided clip is more robust and makes the ROM-screen indexing contract self-contained.

## Rendering and lifecycle observations

- `RobotronGame.Draw()` renders once to a 640x400 render target and then scales that target into the fitted window destination. `SpriteSortMode.Immediate` means custom shader passes are applied at each draw, while pass-through state must be restored after each custom operation.
- `HudLayout.ToPortX/ToPortY` and the tunnel's `ToPixelX/GetRowY` use fixed proportional or rounded coordinate conversion. Horizontal tunnel spans extend to the next mapped pixel and vertical spans tile the next mapped row, avoiding seams.
- Williams and tunnel state are frame-local, with no GPU texture allocation per frame. Williams stores 304x256 palette bytes; tunnel stores 108-ring lists in the worst case and redraws them every frame. The 108-ring lifetime is bounded, but the repeated full-ring draw is intentionally required for accumulated effects.
- Runtime texture construction in `TextureFactory` uses the graphics device once to create a texture and uploads a complete `Color[]`. There is no per-frame allocation except caller pixel arrays and collision masks.
- `SpriteCollision` caches masks by `Texture2D` reference. This prevents repeated GPU reads, but the cache has no explicit ownership/disposal policy and should be considered device-resource state. There is no dynamic cache growth outside textures loaded or generated by `TextureSet`.
- `ContentTextureSource` delegates loading to `ContentManager`; runtime-generated textures delegate to `TextureFactory`. Both implementations satisfy `ITextureSource`, and no class creates resources in `Update/Draw`.
- `TextureSet` is a load-time aggregate. Its array lengths and names are tied to ROM/frame layouts. Missing assets will fail at load, but it does not silently substitute an incorrect frame after construction.
- `Presentation` returns a uniformly scaled, centred canvas; integer mode never downscales below 1x. Negative destination coordinates are used intentionally for client-area cropping.
- `ArcadeText` advances measured glyph widths consistently for drawing and measurement, and unknown/small-font characters have a deliberate large-font fallback. It does not clip strings itself; callers and the window render target provide clipping.

## Resource and frame-lifecycle recommendations

1. Add explicit pass-through/MainTech binding instead of relying on `Effect.CurrentTechnique`.
2. Make collision mapping use independent X/Y source-to-destination ratios for each sprite.
3. Add complete bounds and zero-dimension guards at mask utility entry points.
4. Add explicit ownership/disposal documentation for generated `Texture2D` resources and masks if the code later supports graphics-device recreation or texture unloading.
