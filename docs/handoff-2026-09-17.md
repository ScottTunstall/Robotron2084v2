## 1. HARD RULES

0. **SOURCE HIERARCHY (author's directive, 2026-09-16): `ref/original-source/*.ASM` is the
   GOSPEL — the authority for SEMANTICS. `asm/robomame.asm` (the annotated R5 disassembly)
   is a GUIDE ONLY:** use it to find code and R5 addresses/data, but never as the authority
   for what something MEANS, and do not trust its comments (at least one is flatly wrong:
   the `$5C23` comment contradicts its own `BNE`). The Gospel names and documents its
   fields; that naming resolves ambiguity. Byte-level DATA (sprites, tables, code the OS
   ROM owns) still comes from the verified ROM image. **The OS routines (the `$D0xx`
   vector table in `RRF.ASM`) exist ONLY in the disassembly** — for those, the disasm's
   code is all there is, and that is fine: it is the actual R5 bytes, not a paraphrase.

   must run, or something genuinely blocking). At the END of the message:
   `powershell -NoProfile -Command "[console]::beep(1000,300); [console]::beep(1400,300)"`.
   **Do NOT beep because a turn or phase finished.**

   `docs/arcade-fidelity-notes.md` in the same commit.

   finding, then write the code).

   deviation or open question.
6. **Do NOT kill a running `Robotron2084.exe` without asking.** The author is usually
   playtesting, and it LOCKS `bin/Debug/net10.0/Robotron2084.exe` so the build fails with
   MSB3027/MSB3021. Ask them to close it (they will). Build both configurations so a
   launch cannot pick up a stale `bin/Release` copy.
7. **`asm/` and `ref/` are gitignored.** `grep_search` cannot see them unless you pass

8. **PowerShell quirks:** no `&&` (chain with `;`); `$NAME` inside a double-quoted string
   is silently eaten, so write commit messages to a file and use `git commit -F <file>`.
9. **THE COMMENT BAR (author's directive, 2026-09-20, notes §111): *"THE CODE SHOULD EXPLAIN HOW THE
   SYSTEM WORKS NOT THE COMMENTS. Only COMPLEX code should be commented, unless you need to xref the
   original arcade source."*** A comment earns its place only as (a) arithmetic the operands do not
   show (the explosion's diagonal lean, a `* 6` accumulator conversion) or (b) a `// ROM: <routine>`
   xref — which §109.7's rule 0 already makes mandatory. Never restate the line below the comment,
   never state a number the code could change, and use no invented vocabulary: an entity's periodic
   action is a **beat** (the name the code already uses — `_beatTimer`/`BeatPeriod`), never a
   "wake-up"; the ROM's own routine names stay (the attract interpreter IS `SPWAKE`).
10. **CONSTANTS, NOT LITERALS (author's directive, 2026-09-20, notes §112): *"use constants with xmldocs
   rather than hard coded values."*** Every literal becomes a named constant whose `<summary>` says what
   it IS and where the number comes from — the ROM routine and the frames it counts, a measurement, or
   the author's tuning — and tunables live in `Tuning/GameplayConstants.cs`. A raw `5`, `6` or `16` in an
   entity is a bug in waiting, and rule 9 forbids explaining it with a comment. **The open job: the
   timer unit (5 per tick, 6 per arcade frame) is written longhand 106 times across `src/`, spark first**
   — see B48i and notes §112.
11. **CLEAN CODE IS THE STANDARD (author's directive, 2026-09-20, notes §114): *"we adhere to clean code
   here - at least the Single Responsibility Principle, method naming, well named variables, consistency
   throughout the codebase, no magic numbers, and above all, READABILITY FOR HUMANS."*** One job per
   class and method, with the name saying WHICH job (`RollOffsets`, `PickDirection`, not `Process`);
   variables named for what they hold in the game's terms, unit included when it matters; one idiom per
   concept across `src/` (a constant in EVERY entity, not three of them); no magic numbers (rule 10);
   and complexity is SPLIT, never suppressed (§99/D-020, no suppressions in the repo). Rename beats a
   comment, a constant beats a literal, a name beats prose. **Not a licence to churn** — no reformatting
   for its own sake, but any file opened for another reason gets this standard while it is open.

## 6. TRAPS THAT HAVE COST TIME (read before debugging anything)

0. **A playtest that disagrees with the ROM means the DECODE is wrong — and the
   disassembly's own comments are the fastest way to find out how.** Three decodes
   survived every test, gate and render gate and were still wrong (§67, §69): the
   explosion's shape, the grunt's speed ramp, and — later the same day — which AXIS the
   explosion cuts on. `asm/robomame.asm` states all three outright ("A = the direction
   the enemy's TOP HALF must explode…", "the delay value … is updated when grunts are
   killed", "$A7 = Y coordinate"), so grep the DISASM for the routine's address and read
   its header BEFORE re-deriving anything from the sources alone. Note the §69 flavour of
   this trap: the sources were read, the branch was found, and the two bytes were simply
   mis-assigned (`LASDIR` is the shot's X step, `LASDIR+1` its Y step) — so when a routine
   has two mirrored branches, check which BYTE each one reads (here: `$A6` = the collision
   COLUMN, `$A7` = the ROW — `STU $A6` is a big-endian 16-bit screen address).
   **A HIT POINT IS NOT A CENTRE.** When a routine has two paths — a collision-anchored one
   and a centred one — the playtest decides which the arcade shows, and the *named* invariant
   is the anchor to trust (`YCENT − YOF == the picture's top`; `NWCENT` sets both to the
   picture's middle). Three explosion reports in a row came from picking the wrong branch or
   reading only one of a routine's passes (§67, §69/§71, §72, §73).
   **And when a routine's body is in front of you, read EVERY blit/loop it performs before
   deciding what is drawn** — three of the last four explosion/brain defects came from
   reading one of a routine's passes and assuming the rest (§67's stale two-half header,
   §71's stale `$473F` comment, §72.1's second blit in `$1DAF`). A routine that fills a
   rectangle is not necessarily a routine that ONLY fills it.

1. **A failed build makes the test run meaningless.** The test EXE is left at its previous
   build, so it reports the OLD set as passing. Confirm "Build succeeded" first.
2. **A stale `bin/Release` copy** — four `Robotron2084.exe` files exist (src + tests ×
   Debug + Release). Timestamp them before concluding a fix "did not work".
3. **The running game locks the exe** (MSB3027/MSB3021 on `bin\Debug`). Ask, never kill.
4. **`asm/` and `ref/` are gitignored** — pass `includeIgnoredFiles: true` to grep.
5. **A leaked pixel-shader pass** (§40, §57): `effect.CurrentTechnique.Passes[0].Apply()`
   is DEVICE state; with `SpriteSortMode.Immediate` it outlives the draw. Any new draw
   helper must call `UsePassThrough()`.
6. **Pass B's "NOT FOUND in ROM" is a PARSER verdict, never evidence of absence** (§52).
   Six-byte ANIMATED descriptors defeat it; find the address or add a pass.
7. **A sprite extracted at the WRONG SIZE is worse than a missing one** (§54) — check
   `(offset, widthInBytes, height)` against the author's repository.
8. **The ROM's velocity units are not pixels** (§55): a COLUMN is 2 px, so "half a column"
   (`CLRB/ASRA/RORB`) is one pixel. `PortTicks(n) = n*6/5` TRUNCATES — use the 6ths
   accumulator idiom for any body of N ROM frames.

   writes white masters + marker variants; `SpriteExtractor` writes palette-coloured
   pixels and now skips them. If you see a generated asset "mysteriously reverting",
   check for a SECOND writer before reverting it — a correct extractor run was once
   reverted as "the suspicious change" while the real bug was in the other tool.
10. **`ImageGrab.grab` copies SCREEN pixels**, not window pixels — raise the target window
    (`SetWindowPos(HWND_TOPMOST)`) or you will measure whatever is on top.
