## 2. THE GATES (exact commands, from the repo root)

```powershell
# 1. Build — expect "0 Warning(s)" and "0 Error(s)" (also build -c Release)
dotnet build Robotron2084.slnx

# 2. Tests — the EXE, not `dotnet test` (the MTP runner misreports)
.\tests\Robotron2084.Tests\bin\Debug\net10.0\Robotron2084.Tests.exe
#    the invariant is "Errors: 0, Failed: 0, Skipped: 1" (the known skip, C2 below).
#    278 total at the end of session 5 — the count grows with every added test.

# 3. Launch smoke — the game must survive 12 s (the bash `timeout` form does NOT work here)
python -c "import subprocess,time; p=subprocess.Popen([r'src\Robotron2084\bin\Debug\net10.0\Robotron2084.exe']); time.sleep(12); print('ok:', p.poll() is None); p.kill()"

# 4. Playfield render check — expect "PASS: playfield interior has content"
python tools\verify-playfield.py

# 5. Font glyph check — expect "PASS: 78 font glyph PNGs match the ROM" (masters only — §92)
python tools\verify-fonts.py

# 6. Attract loop check (~30 s) — expect "PASS: attract mode (title -> demo -> title) works"
python tools\verify-attract.py
```

**Why 4 exists:** the smoke test only exercises the TITLE screen; a regression (§40) hid
every sprite while the wall kept drawing. **Why 5 exists:** every glyph PNG was mirrored
inside each byte for a day (§60) while sizes, counts, the tests and both render gates
stayed green — a generated asset needs a check that reads the ART back. Run 5 after ANY
font regeneration (`python tools/extract-fonts.py`). **Why 6 exists:** nothing else
exercises the attract demo — it saves `attract-title.png` / `attract-demo.png` /
`attract-back-to-title.png` (gitignored) for the author's eyes. Run it whenever the
title screen, the demo AI (`DemoPlayerInputSource`) or a state transition changes.

Test counts drift — **the invariant is `Failed: 0, Errors: 0`, and exactly 1 skipped.**
Keep both configurations built, or a launch may pick up a stale binary.

## 4. What was done on 2026-09-17 (sessions 3, 4 and 5 — the PROG's death, the SPHEROID's chain, and the ATTRACT mode)

Commits, oldest first: `e497b0d` `b1e063e` `f68e6a3` `769e740` `c471042` `12444e8` `4c824be` `d5b956d` `c4e6b2a` `4e11db5` `897777b` `57140a8` `0af889f` `41c19f0` `95a7d04` `0c88056` `3f73e57` `9208af2` `e738979` `3075406` `eacd065` `db94e49` `97ce07f` + the FONTGLYPH commit (find it by message — it updates this list, so its own hash cannot appear in it) **The end-of-session summary — the traps, the two deliberate deviations and the open questions — is notes §89; read it before anything else.**

- **Wave-start materialisation (notes §62) — the robots ASSEMBLE.** `RRG23`'s `APPEAR`
  makes one appear record a frame (every fourth one horizontal), anchored on the robot's
  own centre, and holds the robots OFF for the whole sequence: `PlayField` now queues the
  wave's robots, advances one appear per frame from the shared ten-record pool, and skips
  a materialising robot in both `UpdateEntities` and the draw. `IArtSource` was split out
  of `IExplodable` because the hulk materialises but can never explode. The player's own
  appear (`PAPPR`) is deliberately NOT implemented (the port's grace cannot freeze the
  field the way the ROM's start sequence does).
- **The wall and the laser-wall flare are per-wave palette tables (notes §63).** `GTWCOL`
  sets FOUR per-wave slots, not two: `WALCOL` (the BORDER colour — wave 1 ORANGE, wave 9
  BLACK) and `LASCOL` (RRF.ASM's "LASER WALL COLLIDE COLOR" — the FLARE where a laser runs
  off the field, solid on a left/right wall, dithered with the wall colour on a top/bottom
  one). The port had hard-coded slot 11 for the wall and drew no flare at all.
- **The HUD is the arcade's now (notes §58).** Score: the ROM's eight digit positions
  (10M masked off, then 1M..units) with leading zeros blanked but still advancing the
  cursor (6 px vs 7 px) and the **last two digits always drawn**; P1 col 21 / P2 col 85,
  row 14 (**not** row 20 — that was a bad decode and is why round 8 saw the HUD on the
  wall). The **current** player's score is in slot 10 (a CYCLING slot, `$AA`) and an idle
  player's in slot 1 (`$11`). Men: the 6x8 mini man picture (`MNPIC`) beside the score,
  8 px apart, capped at seven, drawn with its own palette slots (slot 11 cycles). The wave
  indicator is the ROM's bottom-of-screen "<n>  WAVE". The port's top-right "LEVEL n" is
  gone.
- **Two-player mode (notes §59)**: `1` / `2` on the title screen; per-player score, lives
  and wave; the turn passes on a death while the other has men; a wave clear keeps the
  same player; both scores go to the high-score table. `PlayerSlot.Input` is per-slot for
  the future SIMULTANEOUS mode.
- **The font glyphs were mirrored inside every byte (notes §60)** — fixed, regenerated,
  and `tools/SpriteExtractor` no longer writes font glyphs at all.
- **The explosions are the Gospel's now (notes §61, `e72b424`)** — three engines behind
  one dispatch (RRX7's `EXSTV`): a diagonal shot fans the sprite's rows at 45 degrees
  (RRDX2), a pure vertical shot takes the HORIZONTAL explosion, a pure horizontal shot
  the VERTICAL one (**the axes in this bullet were backwards until §69 — see below**).
  The fan is anchored at the IMPACT (the laser/robot overlap centre, the ROM's `CENTMP`),
  its size is the ROM's own `$100`-a-frame accumulator (15 draws, steps 2..16) against
  ONE pool of ten records shared with the APPEAR, and strips outside the playfield are
  DROPPED. §35.3 is CORRECTED: the player death is RRX7's `PDTHV` — a solid-colour
  flicker then the slot-12 fade — NOT a strip cascade, so that fade is the §33 mechanism
  (still open with the author).
- **The explosion: its axes AND its shape, and both were wrong (notes §67 / §69 / §71).**
  Three author reports in one day — *"the explosions are completely wrong"*, *"when you shoot
  enemies vertically aren't they supposed to explode horizontally?"*, *"the vertical
  explosion only explodes upwards — it's meant to be up AND down at the same time"*. What
  came out of them: (a) the **axes** — a vertical shot cuts the sprite into COLUMNS (they
  fly apart left/right), a horizontal shot into ROWS (up/down), a diagonal into rows with a
  lean (§69); (b) the **shape** — ONE fan, not two halves: `base = YCENT − step*YOF +
  step/2` and `segment i = base + i*step`, so the base climbs while the segments march down
  and the fan opens both ways at once (§71 — §67's two halves came from a *stale* header
  comment that `$473F` itself never honours); (c) the diagonal lean is `±2×(step>>1)` for
  the whole fan, and the spacing unit is one strip WIDTH (1 px for a row, 2 for a byte
  column); (d) the record's clock — one step per ROM FRAME, not per port tick (18 ticks per
  record, §65's class). The grunt ramp was the first report's companion: the ROM's `×7/8`
  only applies while it stays ≥ the floor, and only the SHARED limit changes (survivors keep
  their countdowns), so wave 1 now ramps 20→17→14→12→10 and stops. **Sound is off by
  default** (§68, `Sound.Enabled`, or `ROBOTRON2084_SOUND=1`).
- **Two more visual defects, both decode errors again (notes §72).** *"When the brain progs
  a human, the brain sometimes turns into a square block!"* — the ROM's `$1DAF` does TWO
  blits (fill the brain's rectangle with `$BB`, then blit the brain's own picture over it,
  `JMP $D018`); §46/§47 read only the first, so the port drew the bare block. The block is
  a backdrop and the sprite is drawn on top again. *"The vertical explosion works
  sometimes, but doesn't last very long"* — the vertical-shot (H) engine's spacing unit was
  counted in BYTE columns (2 px) where `RRHX4`'s `WRITE` walks PIXELS (`ASLA` "DOUBLE FOR
  PIXEL WIDTH"), so the fan flew off the playfield at twice the arcade's rate; `unit = 1`
  fixes it (frame 0 reconstitutes the sprite, the last frame keeps 7-8 of 8 strips on
  screen). The lifetime was re-derived and is unchanged: `RRS22`'s `TIMER == 2` gate is ONE
  video field (`IRQV` counts twice per field), so 15 frames ≈ 0.30 s is the arcade's. Both
  were settled by a measured dump (a temporary test, deleted before commit) rather than by
  guessing.
- **D-019: no operator/service subsystem** (author, 2026-09-17) — no self-test /
  adjustment screens, no switch/ROM/RAM/colour-RAM tests, no CMOS settings, no
  bookkeeping totals, no coin or free-play handling. START 1 / START 2 stay (they pick
  1 or 2 players).

- **The wave-complete tunnel, built and then tightened four times (notes §79-§85).** `$2AAF: JSR $5700` is `DRAW_COLOUR_CYCLING_TUNNEL_EFFECT` ($5703) with its ring primitive `DRAW_RECTANGULAR_PART_OF_TUNNEL` ($5A11), and it REPLACED the port's invented "LEVEL n COMPLETE" banner — the arcade shows no text at a wave clear. It EXPANDS from a 2-row box at the screen's middle (corners `$3B80` to `$5A82`), 2 rings a task pass, one column left/right and two rows up/down per ring, 54 rings to `$0616`, then the SAME walk again with the colour forced to 0 to erase it. It accumulates: every ring stays on screen, which is what fills the play area, and the black pass takes it away again from the centre out. The pace is the one number taken from the author's playtest rather than the disassembly (~2 s; `PassFifths = 2 * 6`, notes §83) because `ALLOCATE_TASK`'s "A x 16 Millisec" puts the whole effect at 0.86 s and the playtest says otherwise. **Its hatch is the geometry, not a dash pattern:** one ROM pixel per edge, one palette slot per ROW (the 15-pair colour chain), two-pixel MIRRORED vertical edges, and rows that tile edge to edge (notes §85) — see B20. **The SIZE of its bars is the effect's own PALETTE** (notes §86): the walk leaves one slot per row, so the arcade's five-row bars with one-row dark seams come from a colour-cycling RAMP palette (twelve tables in the walker's own ROM block, three slots blacked per pass) — see B21. P still skips a wave (`KeyboardPlayerInputSource`).

- **Prog movement + the quark's first tank (notes §87).** *"Fix the prog movement, the quark birth speed."* (a) `PRGAL/PRGAR`'s ±2 is added to `OX16`, a **screen address** (`column*256 + row`), so it moves 2 **columns** = 4 px a body, and `PRGAD/PRGAU`'s ±4 rows give the same 4 px: the old "vertical progs move twice as fast" read the column as a pixel and the horizontal walk ran at half speed. The aim offsets are in columns as well (±28 columns = ±56 px — the port had ±28 px, and its wrap margin 48 px instead of 48 columns). (b) The quark's first-drop countdown is decremented only on the pass that WRAPS its idle animation, so it counts cycles of six bodies — the author's "the Quarks are dropping tanks WAY too quickly". The drop-phase cadence (every body, `RND(1..TDPTIM/2+1)`) was already right, and §77.2's "tank column" suspicion is cleared: the port does hand the quark ENFNUM.

- **The family's start of wave, and the electrodes (notes §88).** *"At the start of the level, the family members wait too long before they start moving. Also can you check if they should spawn on top of electrodes? I don't think they should."* The ROM creates the humans early, the stagger (`SEED&7+1`) is their first wait and `HUMAN` has no STATUS gate — so the family walks while the robots are still assembling and while the player is in the start grace. The port held them with the robots and added an extra step period (~2.4 s of standing); both are gone, and the human contacts are now gated on the same held state (the ROM only creates `COLCHK` immediately before `CLR STATUS`). On the electrodes: the ROM's own placement is a bare `RANDXY`, so the arcade CAN leave a human stuck inside a post — the port's rule against it is a DELIBERATE deviation the author asked for (the second, after the walk period), now documented as such and made airtight.

- **The spheroid's picture chain — five pictures, one a body (notes §91).** *"The spheroid, after giving birth to all the enforcers, looks weird animation wise."* The escape advanced its picture every port TICK instead of once per `NAP 2` body (3.6x: a 15 Hz flicker of four growth frames), and the picture count was one short: `CIRCLE` and `CIRC3L` both wrap at **`CIRP4`** (`CMPD #$1502 / BLS` — the `BLS` STORES `CIRP4`; R5 does the same at $11B6/$1239), so those phases cycle FIVE pictures while only `CIRC2L` wraps at `CIRP7`. The art is one growth animation (dot → plus → small ring → ring-with-hole → medium ring → big ring → opening ring → fragments), so the idle spin pulses to the medium ring and the drop phase grows to the burst the enforcer pops out of. `Spheroid` now runs the ROM's chain end to end: one pointer, one entry per body, the phase's countdown and the escape's X exit test on the WRAP pass (so the escape can overshoot the exit column or wait at the wall for its next wrap), the drop phase carrying on from `CIRP4` into `CIRP5`, a spheroid born on `CIRP4`, and the freeze gate only on the spin phase. **Also flagged, not changed:** the generic mover adds its velocity per 60 Hz TICK where `OPB80` adds it per ROM FRAME, so spheroid/spark/missile motion is 20% fast.

- **The prog's death, and the corrupt burst art (notes §90).** *"Now, when I shoot the progs (after they have been programmed) the explosion effect looks weird."* Two defects. (a) `ProgBurst.png` **decoded to noise**: it is the port's only INLINE sprite (`PGXPIC` is not in the R5 ROM, so `tools/SpriteExtractor` carries the source's `PGXD` bytes in the program), and nine of its sixteen rows had been written as EIGHT bytes instead of six — the writer reads exactly `w*h` = 96 bytes, so it walked a misaligned stream out of a 114-byte array. Fixed from the listing, verified by decoding the PNG back to palette indices, and the extractor now REJECTS inline data whose length is not exactly `w x h`. (b) The death was wrong in KIND: `PRGKIL` erases the trail, swaps the object's **picture descriptor** to `PGXPIC`, clamps the corner and then `JSR EXST` — a RAM vector (`RRF.ASM:262`) holding `JMP EXSTV` — so a prog dies in the SAME strip explosion as every other robot, fed the 12×16 card. `Prog` is now `IExplodable` (art = `ProgBurst`, instant `Kill`, no `Dying` phase), and the new defaulted `IExplodable.ExplosionBounds` gives `EXSTV`'s rect (`UL = OBJX/OBJY` with the PICTURE's W/H) — the card's rect at the prog's corner, not the card centred in the smaller human box. The kill also now plays the sound it never reached (`PGKSND` = `SoundTables.RobotDeath`).

## 6. TRAPS THAT HAVE COST TIME (read before debugging anything)

0. **A playtest that disagrees with the ROM means the DECODE is wrong — and the
   disassembly's own comments are the fastest way to find out how.** Three decodes
   survived every test, gate and render gate and were still wrong (§67, §69): the
   explosion's shape, the grunt's speed ramp, and — later the same day — which AXIS the
   explosion cuts on. `asm/robomame.asm` states all three outright ("A = the direction
   the enemy's TOP HALF must explode…", "the delay value … is updated when grunts are
   killed", "$A7 = Y coordinate"), so grep the DISASM for the routine's address and read
   its header BEFORE re-deriving anything from the sources alone. Note the §69 flavour of
   this trap: the sources were read, the branch was found, and the two bytes were simply
   mis-assigned (`LASDIR` is the shot's X step, `LASDIR+1` its Y step) — so when a routine
   has two mirrored branches, check which BYTE each one reads (here: `$A6` = the collision
   COLUMN, `$A7` = the ROW — `STU $A6` is a big-endian 16-bit screen address).
   **A HIT POINT IS NOT A CENTRE.** When a routine has two paths — a collision-anchored one
   and a centred one — the playtest decides which the arcade shows, and the *named* invariant
   is the anchor to trust (`YCENT − YOF == the picture's top`; `NWCENT` sets both to the
   picture's middle). Three explosion reports in a row came from picking the wrong branch or
   reading only one of a routine's passes (§67, §69/§71, §72, §73).
   **And when a routine's body is in front of you, read EVERY blit/loop it performs before
   deciding what is drawn** — three of the last four explosion/brain defects came from
   reading one of a routine's passes and assuming the rest (§67's stale two-half header,
   §71's stale `$473F` comment, §72.1's second blit in `$1DAF`). A routine that fills a
   rectangle is not necessarily a routine that ONLY fills it.

1. **A failed build makes the test run meaningless.** The test EXE is left at its previous
   build, so it reports the OLD set as passing. Confirm "Build succeeded" first.
2. **A stale `bin/Release` copy** — four `Robotron2084.exe` files exist (src + tests ×
   Debug + Release). Timestamp them before concluding a fix "did not work".
3. **The running game locks the exe** (MSB3027/MSB3021 on `bin\Debug`). Ask, never kill.
4. **`asm/` and `ref/` are gitignored** — pass `includeIgnoredFiles: true` to grep.
5. **A leaked pixel-shader pass** (§40, §57): `effect.CurrentTechnique.Passes[0].Apply()`
   is DEVICE state; with `SpriteSortMode.Immediate` it outlives the draw. Any new draw
   helper must call `UsePassThrough()`.
6. **Pass B's "NOT FOUND in ROM" is a PARSER verdict, never evidence of absence** (§52).
   Six-byte ANIMATED descriptors defeat it; find the address or add a pass.
7. **A sprite extracted at the WRONG SIZE is worse than a missing one** (§54) — check
   `(offset, widthInBytes, height)` against the author's repository.
8. **The ROM's velocity units are not pixels** (§55): a COLUMN is 2 px, so "half a column"
   (`CLRB/ASRA/RORB`) is one pixel. `PortTicks(n) = n*6/5` TRUNCATES — use the 6ths
   accumulator idiom for any body of N ROM frames.
9. **Two tools writing one asset** (§60): `tools/extract-fonts.py` owns the fonts and
   writes white masters + marker variants; `SpriteExtractor` writes palette-coloured
   pixels and now skips them. If you see a generated asset "mysteriously reverting",
   check for a SECOND writer before reverting it — a correct extractor run was once
   reverted as "the suspicious change" while the real bug was in the other tool.
10. **`ImageGrab.grab` copies SCREEN pixels**, not window pixels — raise the target window
    (`SetWindowPos(HWND_TOPMOST)`) or you will measure whatever is on top.
