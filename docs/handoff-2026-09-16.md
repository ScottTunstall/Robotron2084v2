  has no XSIZE field). The port has one engine and no lean-free path, so it
  draws a leaning fan for every kill — wrong in KIND.
- **`$46E6` is `APSTZ` = START AN APPEAR** (rows CONVERGING), not an explosion

  `AWRITE` is also the wave-start materialise effect.

## 6. RECIPES (how to do the common jobs)

### 6.1 Research a ROM address
1. `grep_search` with `includeIgnoredFiles: true` and
   `includePattern: "asm/robomame.asm"` for the label or the hex address.
   The format is `LABEL:` then `ADDR: BB BB BB  MNEMONIC  OPERANDS  ; comment`.
2. Cross-check against `ref/original-source/<MODULE>.ASM` (readable 1982
   source, but note it is an EARLIER revision — field offsets differ from R5).
   With `asm/` closed, the source listing is the only readable version, so use
   both.
3. Byte-level authority is `ref/rom/robotron64k.bin`.

### 6.2 Verify visually (the author cannot see their own screen — the harness overlaps it)

  window. **`SendInput` alone does NOT work** — it goes to whatever is

- **`verify-playfield.py` CAN MEASURE THE WRONG WINDOW (2026-09-16).**
  `ImageGrab.grab(bbox=…)` copies SCREEN pixels, not window pixels, so a maximised
  browser sitting over the game was what got counted — the tool PASSed at 99.77% lit.
  It now raises the game with `SetWindowPos(HWND_TOPMOST)` first (the only raise that
  works; `SetForegroundWindow` returns 0 here) and FAILs if the raise fails or the
  interior is implausibly bright (>50% — a real playfield reads ~3%). **ctypes trap:**
  `SetWindowPos` silently returns 0 unless you declare `argtypes`/`restype`, which is
  what made the first attempt at this fix appear to do nothing.
- **A FULL `SpriteExtractor` RUN REWRITES 78 FONT PNGs WITH DIFFERENT PIXELS
  (2026-09-16).** The fonts are authored by `tools/extract-fonts.py`; the two tools
  disagree, so an extractor run clobbers the other's output. Always `git status`
  after a run and `git checkout -- src/Robotron2084/Content/Sprites
  docs/sprite-map.md` before committing anything else. Its warnings are worth reading —
  but they are a PARSER verdict, NOT proof the data is absent: `MTNKP1..4` were reported
  "NOT FOUND in ROM" and were sitting at `$5036`/`$503E`/`$505A`/`$507A` all along
  (Pass C extracts them now, notes §52). `SHLP1` may be the same story.

1. **A custom shader effect used inside a SpriteBatch must NOT declare a
   vertex shader.** `ColorCycle.fx` is bound manually per draw
   (`SpriteSet.DrawSprite` → `effect.CurrentTechnique.Passes[0].Apply()`), not
   via `SpriteBatch.Begin(effect:)`. `EffectPass.Apply()` binds every stage the
   pass declares, so a VS in the pass REPLACES SpriteBatch's own VS for the
   rest of the batch — and a VS that doesn't apply SpriteBatch's projection
   matrix clips every sprite on screen. That was the "only the wall renders"
   bug (§40), and it also killed the HUD text and life icons, which pass no
   effect at all. **Keep the pass pixel-shader-only.** If a custom VS is ever
   genuinely needed, the draw must move to `SpriteBatch.Begin(effect: ...)`.
   **AND the same leak applies to the PIXEL stage (2026-09-16, notes §57):** a pass bound
   by `Apply()` OUTLIVES the draw that made it, so any later plain `spriteBatch.Draw` is
   rendered through it. Every helper drawing something that is NOT a remap must call
   `SpriteSet.UsePassThrough()` (it rebinds `MainPS`), and every remap draw must hand the
   pass back afterwards. The symptom is a fill painted in a colour nobody asked for —
   that is how the prog's ghost cards came out black. **When the author reports a COLOUR,
   suspect the draw path before re-deriving the ROM.**
2. **Don't chase red herrings in the shader.** A previous session "fixed"
   `float4 Position` → `float3 Position` in the VS and it changed nothing — the
   real cause was the missing projection matrix (see 1).
3. **`tools/generate-mgcb.py` owns `Content.mgcb`.** It previously had no
   effect entries and regenerating it WIPED the hand-added `ColorCycle.fx`
   entry (the game then crashed at load). It now emits `Content/Effects/*.fx`
   too. If you add a content file, add it to the generator.
4. **`PlayerInvincibleForTesting` must be a property, not a `const`** (CS0162),
   and flipping it requires the three coordinated edits in C2.
5. **The disasm parser rule** (used by `tools/SpriteExtractor` and any script
   you write): a byte is a **whole whitespace-delimited field of exactly two
   hex digits**, followed by a space or EOL. Never consume hex-looking runs
   inside mnemonics — "ADDD" contains "AD" and "DD", which once produced a
   false 1,649-mismatch count instead of the true 34.
6. **The render checks need a real GPU/window.** They run on the author's
   machine only; they are not CI-friendly without a headless flag.
